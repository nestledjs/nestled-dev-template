## Verifier verdict — `NEEDS_WORK` (round 3)

Scope coverage complete; D3 and "defaults must not shift" both confirmed satisfied. One new blocking
defect, reproduced before acting on it:

**`webOrigin()` returns an explicit `WEB_URL` unnormalized.** `main.ts` matches origins with
`origins.includes(origin)` — exact string equality against the browser's `Origin` header, which is
always bare scheme+host+port. So:

| `WEB_URL` | `cors.origin` | Browser on `http://localhost:4200` |
|---|---|---|
| `http://localhost:4200` | `["http://localhost:4200"]` | allowed |
| `http://localhost:4200/` | `["http://localhost:4200/"]` | **rejected** |
| `http://localhost:4200/app` | `["http://localhost:4200/app"]` | **rejected** |
| `localhost:4200` | `["localhost:4200"]` | **rejected** |

All three are regressions — before this branch `WEB_URL` was never consulted for CORS, so those
configs fell through to main.ts's `['http://localhost:4200']` and worked. Nothing catches it:
`validation.ts` types `WEB_URL` as a bare `Joi.string()` with no origin check (unlike `API_URL`),
and the doctor only compares `urlPort(WEB_URL)` to `WEB_PORT`, which matches for
`http://localhost:4201/`.

The asymmetry marks it as an oversight: the sibling `apiOrigin()` directly above already normalizes,
via a helper `configuration.ts` line 1 already imports. Injected with one caveat — **not** to reuse
`normalizeApiOrigin` as-is, since it also strips a trailing `/api` segment, which is API-specific
semantics with no business on a web URL. Suggested origin-collapsing via `new URL(...).origin` with
a fall-through to the `WEB_PORT`-derived origin for unparseable or scheme-less values, which also
subsumes the wildcard check.
